# ÜRÜN MÜDÜRÜ (PRODUCT MANAGER) - KAPSAMLI SKILL

## ÖZET
Ürün Müdürü, ürünün vizyonu, stratejisi, roadmap'ı ve feature önceliklendirmesinden sorumludur. Müşteri ihtiyaçlarını anlayan, bu ihtiyaçları feature'lere çeviren ve ürünü market-fit bulmasını sağlayan kişidir.

## TEMEL SORUMLULUKLAR

### 1. Ürün Vizyonu & Stratejisi
- Ürün vizyonunu tanımlamak
- 1-3 yıllık stratejik roadmap oluşturmak
- Market positioning
- Competitive differentiation
- Revenue model tanımlama

### 2. Müşteri Anlaşması
- User research
- Customer interviews
- User personas geliştirme
- Customer journey mapping
- Problem statement yazma

### 3. Ürün Gerekçesi (Requirements)
- User stories yazma (As a... I want... So that...)
- Acceptance criteria tanımlama
- Use case geliştirme
- Feature specifications
- Non-functional requirements

### 4. Prioritization & Roadmap
- Feature prioritization (MoSCoW, Value vs Effort, RICE)
- Quarterly roadmap oluşturma
- Sprint planning'de PO olarak katılma
- Backlog grooming
- Trade-off kararları

### 5. Stakeholder Management
- Engineering team iletişimi
- Executive alignment
- Customer feedback collection
- Market feedback analysis
- Launch planning

### 6. Analytics & Metrics
- KPI definition
- Success metrics
- Feature adoption tracking
- Customer satisfaction (NPS, CSAT)
- A/B testing planning

### 7. Post-Launch Management
- Feature adoption monitoring
- User feedback implementation
- Bug tracking ve prioritization
- Performance metrics review
- Next iteration planning

```
ROADMAP PRIORITIZATION FRAMEWORK: RICE

R = Reach (How many users affected?)
I = Impact (How much does it help each user? - 3:Medium, 10:High)
C = Confidence (How sure are we? 0.5-1.0)
E = Effort (How many weeks to build?)

RICE Score = (Reach × Impact × Confidence) / Effort

Example Features:

Feature 1: Native mobile app
Reach: 100K users/quarter (estimated)
Impact: 10 (major - app increases retention)
Confidence: 0.9 (strong user feedback)
Effort: 12 weeks
Score: (100,000 × 10 × 0.9) / 12 = 75,000

Feature 2: SMS notifications
Reach: 500K users/quarter
Impact: 3 (modest - nice to have)
Confidence: 0.8 (good feedback)
Effort: 2 weeks
Score: (500,000 × 3 × 0.8) / 2 = 600,000 ⭐ HIGHEST PRIORITY

Feature 3: AI recommender system
Reach: 800K users/quarter
Impact: 5 (medium-high - helps discovery)
Confidence: 0.6 (uncertain if we can build well)
Effort: 8 weeks
Score: (800,000 × 5 × 0.6) / 8 = 300,000

PRIORITIZED BACKLOG:
1. SMS notifications (600,000)
2. AI recommender system (300,000)
3. Native mobile app (75,000)
4. Insurance integration (...)
5. ...

ACCEPTANCE:
Score > 100,000: Do this quarter
Score 50,000-100,000: Backlog for next quarter
Score 10,000-50,000: Consider for future
Score < 10,000: Park or kill
```

## 3. USER STORIES YAZMA

**Format: As a... I want... So that...**

```
USER STORY TEMPLATE
===================

User Story 1: Charter Booking (Core Feature)

Title: "Sailor and guest can instantly book a charter"

As a: Sailing enthusiast (guest)
I want to: Find available sailing charters, book one in < 5 minutes,
           receive instant confirmation
So that: I can enjoy sailing experiences without planning hassles

Acceptance Criteria:
□ Guest can search by location, date, yacht type
□ Available charters appear within 2 seconds
□ Can book with one click
□ Receive booking confirmation via email & SMS
□ Can view trip details immediately after booking
□ Sailor receives booking notification

Non-Functional Requirements:
- Page load: < 2 seconds
- Search results: < 1 second
- Booking completion: < 30 seconds
- System uptime: 99.5%

Story Points: 8 (medium size)
Priority: CRITICAL (MVP)
Assignee: Backend + Frontend team
Sprint: Sprint 1

Test Cases:
TC1: Search for charters in Barcelona June 2024
TC2: Book available charter with credit card
TC3: Receive confirmation email
TC4: View booked trip in user dashboard
TC5: Cancel booking
TC6: Search with no results

Acceptance Checklist:
□ Feature complete and working
□ All test cases pass
□ Code reviewed & merged
□ QA tested
□ Documentation complete
□ No performance issues
□ Security review pass
□ PO accepted & signed off

────────────────────────────

User Story 2: Rating & Review

Title: "Guest can rate and review their charter experience"

As a: Guest who completed a charter
I want to: Rate the experience 1-5 stars and write detailed review
So that: Other guests can learn about the experience quality

Acceptance Criteria:
□ Receive review prompt after trip ends
□ Can rate: Cleanliness, Communication, Accuracy, Value
□ Can upload photos from trip
□ Can write text review (max 500 chars)
□ Reviews appear on yacht/sailor profile
□ Sailor can respond to reviews
□ Ratings feed recommendation algorithm

Story Points: 5
Priority: HIGH
Sprint: Sprint 3

────────────────────────────

User Story 3: Host Dashboard

Title: "Sailor can view bookings, earnings, and reviews"

As a: Sailor with multiple boat listings
I want to: See all bookings, earnings, reviews in one dashboard
So that: I can manage my business efficiently

Acceptance Criteria:
□ Dashboard shows: Upcoming bookings, past earnings, reviews
□ Can accept/decline booking requests
□ Can see earnings breakdown by trip
□ Can respond to reviews
□ Can adjust pricing per season
□ Can block out dates unavailable
□ Can message with guests

Story Points: 13 (large)
Priority: HIGH
Sprint: Sprint 2-3
```

## 4. SPRINT PLANNING 및 BACKLOG GROOMING

**PO'nun Sprint Planning'de Rolü**

```
SPRINT PLANNING MEETING
======================

Duration: 2 hours
Attendees: PO, Scrum Master, Development Team
Frequency: Every 2 weeks (at start of sprint)

Agenda:

1. SPRINT GOAL (10 min)
   PO: "What do we want to accomplish this sprint?"
   
   Example:
   "Sprint 5 Goal: Complete booking flow MVP and launch beta
   for 100 test users. Gather feedback for refinement."
   
   Team: Agrees or suggests modifications
   Team confirms: "Yes, we can deliver this"

2. BACKLOG REFINEMENT (20 min)
   PO: Presents top priority stories
   - Story 1: Instant booking (8 SP)
   - Story 2: Cancellation policy (5 SP)
   - Story 3: Host messaging (8 SP)
   
   Team: Questions clarifications
   "Is 'instant booking' actually instant or queue-based?"
   "What payment methods are included?"
   
   PO: Answers questions, clarifies acceptance criteria
   
   Result: Stories are well-understood

3. CAPACITY & ESTIMATION (15 min)
   Scrum Master: "Team capacity?"
   Team: "2 devs full-time, 1 dev 50% (on-call)
           = 75 story points capacity"
   
   Team: Selects stories up to capacity
   Total: Story 1 (8) + Story 2 (5) + Story 3 (8) 
        + Story 4 (5) + Story 5 (3) = 29 SP
        + Buffer: 10 SP = 39 SP (51% of capacity)
   
   PO: "Why only 51%?"
   Team: "First sprint, learning curve, unknowns"
   PO: "OK, let's add Story 6 (5 SP) = 44 SP (59%)"

4. COMMITMENT (15 min)
   Scrum Master: "Does team commit to deliver these 6 stories?"
   
   Team: "Yes, we commit"
   (Or if not: renegotiate scope)

5. SPRINT SCHEDULE (remaining time)
   - Daily standups: 9 AM (15 min)
   - Sprint review: Friday 2 PM
   - Retrospective: Friday 3 PM
   - Next planning: Monday 10 AM (Sprint 2)

SPRINT BACKLOG (Result of Planning):

Story 1: Instant Booking (8 SP)
├─ Task 1.1: Backend API (3 days)
├─ Task 1.2: Frontend UI (2 days)
├─ Task 1.3: Testing (1 day)
└─ Task 1.4: Documentation (0.5 day)

Story 2: Cancellation Policy (5 SP)
├─ Task 2.1: Policy model (2 days)
├─ Task 2.2: Refund logic (2 days)
└─ Task 2.3: Testing (1 day)

[... continues for all stories]

────────────────────────────

BACKLOG GROOMING (Before Planning)

When: 1 week before sprint planning
Duration: 1-1.5 hours
Attendees: PO, Tech Lead, Scrum Master (optional)

Purpose: Prepare stories for sprint planning

Agenda:

1. PRIORITIZE
   "What should we do next?"
   
   Current top 20 stories ranked by RICE score
   PO moves stories up/down
   Removes duplicates
   Marks technical debt items

2. CLARIFY
   Tech Lead: "This story is unclear. What exactly?"
   PO: Clarifies requirements, creates sub-stories if needed
   
   Example:
   "Advanced search" → Breaks into:
   - Basic filters (location, date)
   - Advanced filters (boat type, crew count)
   - Saved searches
   - Recommender algorithm

3. ESTIMATE
   Team estimates new stories:
   - Story A: 5 SP
   - Story B: 8 SP
   - Story C: 13 SP (might be too big, break down)
   
   Re-estimate unclear stories

4. READY FOR SPRINT
   ✓ Story has clear acceptance criteria
   ✓ Story is estimated
   ✓ Story has no unknowns
   ✓ Story can be completed in 1 sprint
   ✓ Team understands it

   If not → Mark as "Not Ready" → PO refines more
```

## 5. METRICS & ANALYTICS

**Success Metrics PO Should Track**

```
KEY PERFORMANCE INDICATORS (KPIs)
==================================

PRODUCT METRICS (月次 Monthly)

Growth:
- MAU (Monthly Active Users): Target 50K → 100K → 500K
- New users per month: Target 10% growth
- Sailor growth: Target 5K → 50K
- GMV (Gross Merchandise Value): $100K → $1M → $10M
- Bookings per month: 1K → 10K → 100K

Engagement:
- Average bookings per user/month: 0.5 → 1.5 → 2.5
- Repeat booking rate: 15% → 40% → 60%
- Session duration: Target > 10 minutes
- Feature adoption: % using new features

Retention:
- Day 7 retention: Target > 40%
- Day 30 retention: Target > 25%
- Monthly churn rate: Target < 5%
- Sailor retention: Target > 70% repeat bookings

Quality:
- NPS (Net Promoter Score): Target 40 → 60 → 70+
- CSAT (Customer Satisfaction): Target 4.3/5
- App rating: Target 4.7/5
- Support ticket rate: Target < 1% of bookings

────────────────────────────

FEATURE METRICS (After Launch)

Feature: Instant Booking
- Adoption rate: % of users using it
- Impact on conversion: Did it increase?
- Impact on time-to-book: Did it decrease?
- User satisfaction with feature

Feature: Reviews & Ratings
- Adoption rate: % writing reviews
- Review volume growth
- Average rating over time
- Impact on bookings

────────────────────────────

BUSINESS METRICS

Revenue:
- Total revenue: Booking fees collected
- ARPU (Average Revenue Per User): Revenue / users
- Sailor earnings (for retention)
- Gross margin: Revenue - costs

Unit Economics:
- CAC (Customer Acquisition Cost): Marketing spend / new users
- LTV (Lifetime Value): Average user lifetime value
- LTV:CAC Ratio: Target > 3:1
- Payback period: When does user pay back acquisition cost?

Example: LTV Calculation
────────────────────────
Average user books 2 trips per year
Average booking value: $200
Seaapp fee: 15% = $30 per booking
Annual revenue per user: 2 × $30 = $60
User lifetime: 5 years
LTV = $60 × 5 = $300

CAC: Marketing spend $1,000 / 100 new users = $10
LTV:CAC = $300:$10 = 30:1 ✓ (Great!)

────────────────────────────

TRACKING DASHBOARD (Weekly Review)

User Metrics:
- Total users: [Graph] (should go up)
- MAU: [Graph] (should go up)
- DAU: [Graph] (consistency check)
- New signups: [Graph] (growth rate)

Booking Metrics:
- Bookings/week: [Graph] (should go up)
- Booking value: [Graph] (price elasticity)
- Conversion rate: Visitors → Booking
- Cancellation rate: Should be monitored

Quality Metrics:
- NPS: [Gauge] (aim > 50)
- CSAT: [Gauge] (aim > 4.3)
- Support tickets: [Graph] (should be stable/down)
- App rating: [Gauge] (aim > 4.7)

FunnelAnalysis:
 Visit Website: 10,000
      ↓ (80% enter)
 Create Account: 8,000
      ↓ (50% search)
 Search Charters: 4,000
      ↓ (25% view detail)
 View Details: 1,000
      ↓ (20% book)
 Complete Booking: 200
 
 Conversion Rate: 200/10,000 = 2%
 
 Analysis: Where do users drop off?
 - Between create account & search: 40% drop
   → Maybe search not obvious?
 - Between search & view detail: 75% drop
   → Maybe results bad quality?
 - Between view & booking: 80% drop
   → Maybe checkout too complicated?

Recommendations:
"Next sprint: A/B test search results quality improvements"
```
